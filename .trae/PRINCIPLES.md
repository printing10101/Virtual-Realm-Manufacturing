# Boil the Lake 开发原则

> AI辅助编码技术使完整实现的边际成本显著降低。始终追求功能的完整实现，杜绝仅完成90%的半成品交付。

## 核心原则

### 1. 完整实现原则
当完整实现方案仅比临时捷径多5-15分钟工作量时，**必须选择完整实现方案**。

**执行标准：**
- 拒绝"先这样吧，后面再改"的思维模式
- 评估工作量时，完整方案≤15分钟增量的，一律完整实现
- 每次代码提交必须是功能完整、可交付的状态
- 严禁以"快速迭代"为名交付半成品

### 2. 测试不延期原则
单元测试、集成测试和E2E测试是成本最低的"湖泊"，**必须在当前PR中完成，严禁推迟到后续PR**。

**执行标准：**
- 新功能开发必须同步编写对应测试
- Bug修复必须包含复现测试用例
- 测试覆盖率<80%的代码不得合并
- 禁止使用"后续补充测试"的借口

### 3. 边缘情况原则
所有已知的功能边缘情况和边界条件**必须在当前实现中处理**，代码中**不允许保留"TODO: 后续处理"标记**。

**执行标准：**
- 设计阶段必须识别所有边缘情况
- 已知边界条件必须在本次实现中覆盖
- 代码审查时重点检查未处理的边缘情况
- 拒绝"正常路径先跑通，异常后面再处理"的做法

### 4. 错误处理原则
系统中**每条错误信息都必须包含具体可操作的解决建议**。

**执行标准：**
- 错误消息格式：`[错误类型] 具体描述。建议操作：[具体步骤]`
- 禁止使用笼统的"发生错误"、"处理失败"等模糊表述
- 每个catch块必须提供有意义的错误上下文
- 错误日志必须包含足够的调试信息（请求参数、状态等）

**示例：**
```python
# 错误示例
raise Exception("Failed to process")

# 正确示例
raise ValueError(
    f"模型加载失败: {model_name}。"
    f"建议操作: 1) 检查模型文件是否存在于 {model_path}；"
    f"2) 验证文件格式是否为 .pt 或 .onnx；"
    f"3) 确认磁盘空间充足。"
)
```

### 5. 文档同步原则
代码变更**必须同步更新相关技术文档**，采用自动化工具确保代码与文档的一致性。

**执行标准：**
- 新增API端点必须同步更新API文档
- 修改配置项必须同步更新配置说明
- 变更业务逻辑必须更新架构文档
- 使用CI检查文档与代码的一致性

**自动化检查：**
```bash
# CI流程中执行
python scripts/check_doc_sync.py
cargo doc --no-deps
```

## 技术债务管理

### TODO/FIXME处理规范
- **≤30分钟可完成的TODO**：必须立即实现，不得推迟
- **>30分钟的TODO**：转化为Issue，添加`boil-the-lake`标签，明确优先级和截止时间
- **代码审查重点**：禁止新增"TODO: 后续处理"类注释

### 测试覆盖要求
- 核心业务逻辑：≥90%
- API接口层：≥85%
- 工具函数：≥80%
- UI组件：≥75%

## 检查清单

提交PR前必须确认：
- [ ] 功能完整实现，无明显的TODO标记
- [ ] 测试用例已编写并通过，覆盖率≥80%
- [ ] 所有边缘情况已处理
- [ ] 错误消息包含具体解决建议
- [ ] 相关文档已同步更新
- [ ] 无unwrap()等不安全的错误处理
