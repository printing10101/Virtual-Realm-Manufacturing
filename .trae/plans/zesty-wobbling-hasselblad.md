# 灵境制造优化计划

> 基于深层问题分析，聚焦"做深核心管线"而非"搭更多框架"

---

## 核心原则

**从"框架优先"转向"管线优先"**：先让 DXF→G代码 在真实工厂跑通，再补周边。

---

## 阶段一：核心管线打通（4-6周）

### 1.1 Agent Gateway 实现（P0，1-2周）

**问题**：MCP Server 6个工具裸调 FastAPI，无编排层，无多步推理。

**目标**：实现最小可用的 Agent 编排层。

**具体任务**：
- 在 `python/app/agent/` 下实现 `orchestrator.py`
- 支持 3 种基本编排模式：
  - 顺序链：DXF解析 → 工艺理解 → 参数推荐 → G代码生成
  - 条件分支：根据材料/特征选择不同处理路径
  - 错误回退：某步失败时的降级策略
- 暴露统一接口给 MCP Server 和前端
- 添加基本的执行 trace 记录

**验收标准**：
- MCP 工具可通过 Agent 调用多步管线
- 单次完整管线执行有 trace 日志
- 错误不导致整个流程崩溃

**不做**：
- 不做自主规划
- 不做复杂的状态机
- 不做前端 UI

---

### 1.2 LNN 推理性能真实基线（P0，3-5天）

**问题**：当前 LNN 耗时数据为合成数据（全部 1200.0ms），无法作为真实基线。

**目标**：采集真实推理性能数据，建立可信的性能基线。

**具体任务**：
- 在 `predictor.py` 中添加推理耗时持久化（写入 trace_log.jsonl）
- 记录每次推理的：输入维度、模型版本、耗时、设备（CPU/GPU）
- 清理现有合成数据，标记为 `synthetic: true`
- 运行 100+ 次真实推理，统计 P50/P95/P99

**验收标准**：
- trace_log.jsonl 中每条记录有真实耗时
- 有性能基线报告（至少 100 次推理统计）
- 数据可被 Prometheus 采集

---

### 1.3 切削力模型诚信修复（P0，1周）

**问题**：对外宣称"AI切削力预测"，实际用的是 Kienzle 解析解（1950年代公式）。

**目标**：要么真正实现 ML 切削力预测，要么诚实标注为"解析模型"。

**具体任务**：
- 方案A（推荐）：用 PINN 实现真正的 ML 切削力预测
  - 在 `simulation/cutting_force/` 下实现 `pinn_model.py`
  - 用合成数据训练（先验证 loss 可下降）
  - 推理接口与现有 Kienzle 并行，可切换
- 方案B（最小改动）：在文档和 API 响应中明确标注
  - 当前使用 Kienzle 解析模型
  - ML 模型为"计划中"状态

**验收标准**：
- 方案A：PINN 模型可训练、可推理、loss 下降
- 方案B：所有对外文档和 API 响应明确标注模型类型

---

### 1.4 审计日志激活（P1，2-3天）

**问题**：`audit_log.jsonl` 为空文件，审计系统从未运行。

**目标**：让审计系统真正运行起来。

**具体任务**：
- 检查 `python/app/audit/audit_log.py` 为何未写入
- 确保关键操作（参数修改、方案生成、G代码导出）触发审计
- 添加审计日志写入的单元测试
- 验证日志文件有实际内容

**验收标准**：
- 执行关键操作后，audit_log.jsonl 有新记录
- 单元测试覆盖主要审计场景

## 阶段二：数据底座建设（6-8周）

**对应 SOLO 任务**：M0.2 + M0.3 + M0.5

**具体任务**：

- 验证 MTConnect 适配器可连接 demo agent

**验收标准**：

- 数据正确写入 TDengine
- 采集任务可停止、可查询状态

### 2.2 MachiningRecord 统一数据模型（P1，1周）

**对应 SOLO 任务**：M0.4

**目标**：定义统一的加工记录数据模型。

**具体任务**：
- Pydantic 模型 + SQLAlchemy ORM
- Alembic 迁移脚本
- Repository 模式封装 CRUD
- 与 TDengine 时序数据关联

**验收标准**：
- 迁移可执行
- CRUD 操作正常
- 单元测试通过

---

### 2.3 知识图谱 V1（P1，3周）

**对应 SOLO 任务**：M1.1 ~ M1.3

**目标**：从现有 JSON 数据构建知识图谱。

**具体任务**：
- 设计 4 类核心实体 + 4 类关系的本体
- NetworkX 图存储 + PG 持久化
- 从 materials.json、tools.json、machines.json、process_rules.json 导入
- 生成导入统计报告

**验收标准**：
- 至少 30 个节点 + 50 条关系
- 数据持久化到 PG，重启不丢失
- 可按类型查询节点和关系

## 阶段三：仿真深化（4-6周）

### 3.1 仿真与工艺规划集成（P2，2周）

**对应 SOLO 任务**：M2.3 + M2.4

**目标**：让仿真结果参与工艺方案评估。

**具体任务**：
- 在工艺规划流程中调用仿真器
- 仿真结果作为方案评分的一部分
- 仿真失败不阻塞主流程
- LNN 与仿真结果并行展示

**验收标准**：
- 工艺规划结果包含仿真评分
- 仿真超时/失败时 fallback 到"未仿真"标记

---

### 3.2 贝叶斯 LNN（P2，2周）

**对应 SOLO 任务**：M3.1 + M3.2

**目标**：LNN 支持不确定性量化。

**具体任务**：
- 实现 MC Dropout 贝叶斯近似
- 输出 mean + std
- 新增 `/api/v1/lnn/predict-uncertain` 端点
- 保留原 LNN 接口向后兼容

**验收标准**：
- 推理返回 prediction + uncertainty + confidence
- 推理时间 < 原 LNN × 5

## 暂停/推迟的事项

以下事项建议暂停，等核心管线跑通后再考虑：

- K8s 多副本部署（当前单容器足够）
- Grafana 仪表盘美化（先用简单日志）
- 文档站建设（先用 docs/ 目录）
- ISO 23247 认证准备（产品还没ready）
- Community/Pro 版本划分（先有产品再谈商业化）
- 联邦学习、高级可视化等"锦上添花"功能

---

## 关键提醒

1. **不要跳步**：Agent Gateway 是所有后续任务的基础
2. **不要超范围**：每个任务只做定义内的功能
3. **数据诚信第一**：合成数据必须标注，不能对外声称是真实数据
4. **先跑通再优化**：80% 完成的管线 > 100% 完成的框架
5. **每周验证**：每周至少一次端到端测试，确保管线可用
