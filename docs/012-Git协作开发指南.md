## 1. 项目概述

**灵境制造**是一个AI驱动的3D CAD设计与工艺规划系统，采用以下技术栈：

| 模块 | 技术栈 | 目录 |
|------|--------|------|
| 桌面应用壳 | Tauri + Rust | `src-tauri/` |
| 前端界面 | Vue3 + TypeScript + Vite | `src/` |
| AI后端 | Python + FastAPI | `python/` |
| 文档 | Markdown | `docs/` |

## 2. 快速开始

### 2.1 克隆仓库

**HTTPS方式（推荐初学者）**：
```bash
git clone https://github.com/printing10101/lingjing-manufacturing.git
cd lingjing-manufacturing
```

**SSH方式（需要配置SSH密钥）**：
```bash
git clone git@github.com:printing10101/lingjing-manufacturing.git
cd lingjing-manufacturing
```

**配置SSH密钥（仅首次使用需要）**：
```bash
# 生成SSH密钥（使用GitHub关联邮箱）
ssh-keygen -t ed25519 -C "your_email@example.com"

# 启动ssh-agent并添加密钥
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519

# 复制公钥到剪贴板（Windows PowerShell）
cat ~/.ssh/id_ed25519.pub | clip
```

然后将公钥添加到GitHub：Settings → SSH and GPG keys → New SSH key

### 2.2 安装依赖

**前端依赖**：
```bash
pnpm install
```

**Python依赖**：
```bash
cd python
python -m venv .venv
.venv\Scripts\activate  # Windows
pip install -r requirements.txt
```

**Rust依赖**（首次构建时自动安装）：
```bash
cd src-tauri
cargo build
```

## 3. 分支管理规范

### 3.1 分支模型

本项目采用简化版Git Flow分支模型：

```
main (生产分支)
  └── develop (开发分支)
        ├── feature/xxx (功能分支)
        ├── bugfix/xxx (修复分支)
        └── hotfix/xxx (热修复分支)
```

**分支说明**：

| 分支名 | 用途 | 保护规则 |
|--------|------|----------|
| `main` | 生产环境代码，只接受来自develop的合并 | 禁止直接推送，需要PR |
| `develop` | 集成开发中的最新代码 | 禁止直接推送，需要PR |
| `feature/*` | 开发新功能 | 开发者自由管理 |
| `bugfix/*` | 修复非紧急bug | 开发者自由管理 |
| `hotfix/*` | 紧急生产问题修复 | 开发者自由管理 |

### 3.2 分支命名规则

```
类型/简短描述-问题编号(可选)
```

**示例**：
- `feature/user-auth` - 用户认证功能
- `feature/3d-viewer-improvement-#123` - 3D查看器改进（关联Issue #123）
- `bugfix/fix-cad-export-error` - 修复CAD导出错误
- `hotfix/security-patch-v1.0.1` - 安全补丁

### 3.3 分支工作流

**创建新功能分支**：
```bash
# 1. 切换到develop分支并更新
git checkout develop
git pull origin develop

# 2. 创建并切换到新功能分支
git checkout -b feature/your-feature-name

# 3. 开发过程中定期提交
git add .
git commit -m "feat: 添加XXX功能"

# 4. 推送到远程
git push -u origin feature/your-feature-name
```

## 4. 提交信息规范

### 4.1 提交格式

采用[约定式提交(Conventional Commits)](https://www.conventionalcommits.org/)规范：

```
<类型>(<作用域>): <描述>

[可选的正文]

[可选的脚注]
```

**示例**：
```
feat(cad): 添加STEP文件导出功能

- 实现STEP格式转换器
- 添加导出按钮到UI
- 编写单元测试

Closes #45
```

### 4.2 类型说明

| 类型 | 说明 | 是否触发版本发布 |
|------|------|------------------|
| `feat` | 新功能 | ✅ MINOR版本 |
| `fix` | Bug修复 | ✅ PATCH版本 |
| `docs` | 文档更新 | ❌ |
| `style` | 代码格式（不影响功能） | ❌ |
| `refactor` | 代码重构 | ❌ |
| `perf` | 性能优化 | ✅ PATCH版本 |
| `test` | 测试相关 | ❌ |
| `build` | 构建系统/依赖 | ❌ |
| `ci` | CI配置变更 | ❌ |
| `chore` | 其他杂项 | ❌ |

### 4.3 提交示例

```bash
# 新功能
git commit -m "feat(ai): 集成Ollama本地模型支持"

# Bug修复
git commit -m "fix(workspace): 修复项目文件保存后丢失的问题"

# 文档更新
git commit -m "docs: 更新API接口文档"

# 重构
git commit -m "refactor(cad): 提取CAD生成器公共方法"

# 性能优化
git commit -m "perf(frontend): 优化3D场景渲染性能"

# 带作用域的提交
git commit -m "feat(python): 添加RAG知识库检索接口"
```

## 5. 代码审查流程

### 5.1 审查原则

1. **所有代码必须经过审查才能合并到develop**
2. **至少需要1名其他开发者批准**
3. **CI检查必须通过**
4. **尊重与建设性反馈**

### 5.2 审查清单

**代码质量**：
- [ ] 代码是否清晰易读？
- [ ] 是否遵循项目编码规范？
- [ ] 是否有冗余代码可以简化？

**功能正确性**：
- [ ] 是否实现了需求的所有功能？
- [ ] 边界条件是否处理？
- [ ] 错误处理是否完善？

**测试覆盖**：
- [ ] 是否添加了相应的测试？
- [ ] 测试是否覆盖了主要场景？
- [ ] 测试是否通过？

**性能与安全**：
- [ ] 是否存在性能瓶颈？
- [ ] 是否有安全风险（如SQL注入、XSS）？
- [ ] 敏感信息是否泄露？

## 6. 合并请求(PR)创建步骤

### 6.1 创建PR

**步骤1：推送分支到远程**
```bash
git push -u origin feature/your-feature-name
```

**步骤2：在GitHub创建PR**
1. 访问仓库页面：https://github.com/printing10101/lingjing-manufacturing
2. 点击"Compare & pull request"按钮
3. 或访问：Pull requests → New pull request

**步骤3：填写PR信息**
- **标题**：与提交信息保持一致
- **描述**：使用下方PR模板
- ** reviewers**：指派1-2名审查者
- **Labels**：添加相应标签（feature、bugfix等）
- **关联Issue**：在描述中添加`Closes #XX`

### 6.2 PR模板

```markdown
## 变更类型
- [ ] 新功能 (feat)
- [ ] Bug修复 (fix)
- [ ] 文档更新 (docs)
- [ ] 重构 (refactor)
- [ ] 性能优化 (perf)

## 变更描述
简要描述本次变更的内容...

## 相关Issue
Closes #XX

## 测试说明
- [ ] 已添加单元测试
- [ ] 已进行手动测试
- [ ] 测试用例：...

## 截图（如适用）
[添加截图]

## 注意事项
[需要审查者特别注意的地方]
```

### 6.3 PR审查流程

1. **提交者**：
   - 完成开发并推送分支
   - 创建PR，填写完整描述
   - 指派审查者

2. **审查者**：
   - 查看PR变更的文件和代码
   - 逐行审查代码，提出评论或建议
   - 使用"Request changes"或"Approve"做出审查决定
   - 如有问题，与提交者讨论

3. **提交者回应**：
   - 根据审查意见修改代码
   - 推送新的提交
   - 回复审查者的评论

4. **合并**：
   - 审查通过后，由维护者合并PR
   - 选择"Squash and merge"保持历史整洁
   - 删除已合并的分支

## 7. 冲突解决方法

### 7.1 冲突产生原因

当以下情况发生时会产生冲突：
- 两个人修改了同一个文件的同一行
- 一个人修改了文件A，另一个人删除了文件A
- 合并时两个分支有分叉历史

### 7.2 解决步骤

**场景1：推送时冲突（远程已有新提交）**

```bash
# 1. 拉取远程最新代码
git fetch origin

# 2. 尝试合并远程develop到当前分支
git merge origin/develop

# Git会标记冲突文件，手动编辑解决冲突
# 冲突标记示例：
# <<<<<<< HEAD
# 你的代码
# =======
# 其他人的代码
# >>>>>>> origin/develop

# 3. 标记冲突已解决
git add <已解决的文件>

# 4. 完成合并提交
git commit -m "merge: 解决与develop的合并冲突"

# 5. 推送到远程
git push
```

**场景2：使用rebase解决（推荐，保持线性历史）**

```bash
# 1. 拉取远程最新代码
git fetch origin

# 2. rebase当前分支到最新develop
git rebase origin/develop

# 如果出现冲突：
# - 手动编辑解决冲突
# - git add <已解决的文件>
# - git rebase --continue
# - 重复直到rebase完成

# 3. 强制推送（rebase后需要）
git push -f
```

### 7.3 预防冲突的最佳实践

1. **频繁同步**：每天开始工作前和结束前都拉取最新代码
   ```bash
   git checkout develop
   git pull origin develop
   git checkout feature/your-feature
   git merge develop  # 或 git rebase develop
   ```

2. **小步提交**：频繁提交，每次提交只做一件事

3. **沟通协作**：多人修改同一模块前先沟通

4. **模块化开发**：减少代码耦合，降低冲突概率

## 8. 同步远程仓库更新

### 8.1 拉取最新代码

**方式1：pull（merge方式，推荐）**
```bash
git checkout develop
git pull origin develop
```

**方式2：fetch + merge（更可控）**
```bash
# 1. 获取远程最新但不合并
git fetch origin

# 2. 查看变更
git log HEAD..origin/develop

# 3. 手动合并
git merge origin/develop
```

### 8.2 同步到功能分支

```bash
# 1. 确保本地develop是最新的
git checkout develop
git pull origin develop

# 2. 切换回功能分支
git checkout feature/your-feature

# 3. 合并develop到功能分支
git merge develop

# 或使用rebase（保持线性历史）
git rebase develop

# 4. 如果有冲突，按7.2节解决

# 5. 推送更新
git push
```

## 10. 常见问题解答

### Q1: 我误提交了一个大文件，怎么删除？

```bash
# 从Git历史中删除（需要重写历史）
git filter-branch --force --index-filter \
  "git rm --cached --ignore-unmatch path/to/file" \
  --prune-empty --tag-name-filter cat -- --all

# 然后强制推送
git push origin --force --all
```

**注意**：如果文件已推送到共享仓库，应尽快通知团队其他成员重新克隆。

### Q2: 我想撤销最近的提交怎么办？

```bash
# 撤销提交但保留变更在暂存区
git reset --soft HEAD~1

# 撤销提交并将变更放回工作区
git reset --mixed HEAD~1

# 完全删除提交（危险！）
git reset --hard HEAD~1
```

### Q3: 如何查看某个文件的修改历史？

```bash
# 查看文件完整历史
git log --follow -- <file>

# 查看每行代码的最后修改者
git blame <file>
```

### Q4: 如何配置Git使用代理访问GitHub？

```bash
# 配置HTTP代理
git config --global http.proxy http://127.0.0.1:7890

# 配置HTTPS代理
git config --global https.proxy http://127.0.0.1:7890

# 取消代理
git config --global --unset http.proxy
git config --global --unset https.proxy
```

### Q5: 如何生成和添加SSH密钥？

详见[2.1节 克隆仓库](#21-克隆仓库)中的SSH配置说明。

### Q6: 如何只提交部分变更而不是全部？

```bash
# 使用交互式暂存
git add -p

# 这会逐个变更块询问是否暂存，输入：
# y - 暂存此变更块
# n - 不暂存
# s - 拆分此变更块
# q - 退出
```

## 附录：Git配置推荐

```bash
# 设置全局用户名和邮箱
git config --global user.name "Your Name"
git config --global user.email "your_email@example.com"

git config --global color.ui auto
```
