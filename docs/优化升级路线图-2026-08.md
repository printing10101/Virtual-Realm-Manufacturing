# 优化升级路线图（2026-08）

> 定位：把灵境制造作为公司主力产品推向市场。本路线图回答"从哪些地方入手做全面优化升级"——
> 不仅是代码，更是整个项目。执行原则：**不堆功能、做深信任**；每项完成即在本文件打勾并登记证据。

---

## 0. 总体判断

项目最不缺的是"代码和功能"（后端 1000+ 模块、25 万行、3441 项单测全绿），最缺的是
**信任资产**（真机验证、E2E 回归、交付闭环）。优化重心是四条线并行：

| 主线 | 回答的问题 | 现状 |
|---|---|---|
| A. 核心能力做实 | 客户敢不敢用 | 真机未接（mock 仿真器）、后处理器未实测 |
| B. 质量体系做深 | 承诺能否兑现 | 覆盖率 24%、E2E 曾是空壳（本轮已修复） |
| C. 交付闭环做顺 | 卖出能否装上 | 桌面打包未全新机验证、无自动更新/授权体系 |
| D. 仓库资产治干净 | 长期开发效率 | 双轨制残留、根目录杂物、research/ 未解耦 |

- [ ] **后处理器实测矩阵**
  - 11 种后处理器逐机型在真实机床上试切验证
  - 每机型沉淀 golden NC 输出文件，做回归测试（`pytest.mark.postprocessor`）
  - 产出"机型 × 验证状态"官方支持清单（对外承诺边界）
- [x] **仿真强制闭环**：AI 生成的 NC 代码必须通过体素仿真校验才能导出/下发（产品级流程约束，不只是功能存在）——✅ 2026-09 完成，见 §1「仿真强制闭环」（软件闸门已落地；参数合理性仍靠颤振引擎 + 文献实测数据，实机复核归 L4）

## 3. B 线：质量体系做深（决定承诺能否兑现）

- [ ] **覆盖率棘轮（ratchet）**：`.coveragerc` `fail_under` 只升不降（当前 24%），每次迭代 +1~2%；优先补 `gcode_generation/`、`postprocessor/`、`process_planning/`（直接上机的路径）
- [ ] **清除形式主义测试**：全库扫描 `assert ... in [200, 400, 503]` 式多选一断言并重写（本轮已清掉 cutting_experience 一处）
- [ ] **架构测试违规清零**：`tests/architecture/` 中 `pytest.skip` 降级的遗留分层违规逐个修复，最终移除 skip
- [ ] **双轨制收敛**（定截止日期）：
  - `api/v1/` 平铺路由 vs `api/routers/` 聚合层 → 新路由一律走领域聚合
  - 裸 `HTTPException` vs `AppException` → 新代码一律分级异常
  - 模块级懒单例 vs `dependencies.py` DI → 测试可替换性差的逐个迁移

## 4. C 线：交付闭环做顺（决定卖出能否装上）

- [ ] **桌面打包验证**（发布报告 Go/No-Go 第 2 项）：`npm run app:build` 产出的安装包在全新机器验证「图纸→3D→工艺→NC」全流程 + 重启后 agent 状态不丢
- [ ] **CI 干净环境验证**（Go/No-Go 第 3 项）：GitHub Actions runner 上依赖解析 + 全量测试与本地一致
- [ ] **自动更新**：Tauri updater（签名更新通道），桌面产品没有 OTA 每次升级都是上门服务
- [ ] **崩溃/错误上报**：Sentry 或 self-hosted GlitchTip（制造业客户数据不出厂）
- [ ] **授权体系**：试用期 / 机型模块授权 / 离线激活——后加成本远高于先做
- [ ] **服务端部署形态**：Docker 镜像 + 首启建库验证，覆盖"内网服务器全厂共用"需求

## 5. D 线：仓库资产治干净（决定长期效率）

- [ ] research/（11055 个 py 文件）物理解耦为独立仓库；共享产物以版本化模型文件进入工程侧
- [ ] release 流程固化：tag → 全量测试 → 打包验证 → release workflow 自动化

- 不大重构、不换框架（现架构分层健康）
- 不开新功能线（功能广度已远超信任深度）
