**发布日期**: 2026-07-28

## 一、版本概述

V2.7.0 是灵境制造系统的重大架构演进版本，核心聚焦于**工程模块与研究模块的物理隔离**、**代码质量系统性优化**、**论文实验体系完善**以及**安全漏洞修复**。本版本完成了 V2.6.0 规划中的 Phase 2 解耦任务，建立了清晰的工程边界，同时修复了 15 项分级优化点中的关键问题。

## 二、主要功能变更

### 2.1 工程与研究模块物理隔离

**背景**: V2.6.0 完成了共享契约层建设，V2.7.0 进一步实现工程模块与研究模块的物理隔离，解决代码耦合问题，支持独立演进。

**新增目录结构**:

```
灵境制造（上线版）/
├── engineering/          # 工程模块（1585 个文件）
│   ├── python/           # 后端工程代码
│   │   ├── app/          # FastAPI 应用
│   │   ├── tests/        # 工程测试
│   │   └── requirements.txt
│   ├── src/              # 前端工程代码
│   ├── src-tauri/        # Tauri 桌面应用
│   ├── output/           # 工程输出（颤振预测、G-code 等）
│   └── VERSION           # 工程版本号
│
├── research/             # 研究模块（340 个文件）
│   ├── experiments/      # 论文实验脚本（24+ 个）
│   ├── datasets/         # 研究数据集
│   ├── results/          # 实验结果
│   └── papers/           # 论文相关资源
│
└── shared/               # 共享契约层（V2.6.0 建立）
```

**迁移内容**:
- 前端代码（`src/`、`src-tauri/`）→ `engineering/`
- 后端工程代码（`python/app/`）→ `engineering/python/app/`
- 论文实验脚本 → `research/experiments/`
- 研究数据集 → `research/datasets/`

**价值**:
- 工程模块可独立部署和升级，不影响研究实验
- 研究模块可自由迭代实验代码，不污染工程环境
- 为后续 ONNX 模型加载器、独立测试体系奠定基础

### 2.3 代码质量系统性优化（P0-P3 修复）

基于 V2.6.0 二次代码审计，识别并修复 15 项分级优化点：

#### 2.3.1 P0 级修复（高优先级）

**P0-1: skill_compiler.py 降级路径补 AST 审计**
- **文件**: `engineering/python/app/plugins/skill_loader/skill_compiler.py`
- **问题**: `_compile_code_in_process` 方法（105-128 行）是 RestrictedPython 不可用时的备用编译路径，但未调用 `_audit_code_security` 进行 AST 级别审计
- **修复**: 在 `compile()` 之前调用 `self._audit_code_security(code, skill_id)`，与主路径保持一致的安全基线
- **影响**: 消除潜在的安全漏洞，防止攻击者绕过 AST 审计

**P0-2: ExampleGallery.vue v-html XSS 入口（已验证）**
- **文件**: `engineering/src/examples/ExampleGallery.vue`
- **状态**: `renderMarkdown` 函数（531-570 行）已实现三层防御：
  1. `escapeHtml` 转义所有 HTML 实体
  2. Markdown 语法替换仅生成受控白名单标签
  3. 兜底移除 script/iframe 标签、on* 事件属性、javascript: 协议
- **结论**: 无 XSS 攻击向量，无需引入 DOMPurify

#### 2.3.2 P1 级修复

**P1-6: except Exception 滥用（部分修复）**
- **扫描结果**: 实际 479 处（远超初估 50+）
- **已完成**: 
  - 收窄 5 处可安全收窄的调用点（4 处 `subprocess_op` → `subprocess.SubprocessError`，1 处 DB 操作 → `SQLAlchemyError`）
  - 3 处保留 `Exception` 但添加注释说明原因（yaml 在 try 块内导入无法引用 `YAMLError`）
- **剩余**: 474 处为 generic 类别，需人工逐处判断，列为独立任务

#### 2.3.3 P2 级修复

**P2-7: datetime.now() 未带时区（139 处全部修复）**
- **涉及文件**: 51 个文件
- **修复方案**: 全部转为 `datetime.now(timezone.utc)`
- **保留**: `strftime()` 用于用户可见日期（日志文件名）
- **验证**: 761 个文件编译通过
- **工具**: 提供批量修复脚本 `_fix_p2_7.ps1` 和 `_fix_p2_7.py`

**P2-9: logging_config.py 自测代码 __main__ 守卫（已验证）**
- **文件**: `engineering/python/app/core/logging_config.py`
- **状态**: 567 行已有 `if __name__ == "__main__":` 守卫，自测代码全部位于守卫内部

**P2-8: 异步路径 time.sleep() 滥用（评估为非 bug）**
- **涉及文件**: `plugin_worker.py`、`worker_process.py`、`sqlite_pool.py`
- **评估**: 三处均为同步上下文使用，无 async 滥用，跳过

**P2-10: requests.Session() 未用 with 语句（评估为合理设计）**
- **涉及文件**: `xmaker/integration.py`、`mtconnect/adapter.py`
- **评估**: 采用懒加载 + 显式 close 模式，是 HTTP 客户端最佳实践，跳过

**P2-11: asyncio.run() 在异步上下文（评估为合理使用）**
- **涉及文件**: 15 个文件
- **评估**: 所有 `asyncio.run()` 均有事件循环检测或位于同步入口（CLI/benchmarks/tests/docstring），无真正问题

#### 2.3.4 P3 级修复

**P3-15: 函数内 import json 提到顶层**
- **文件**: 
  - `engineering/python/app/agent/auth.py`（52, 62 行）
  - `engineering/python/app/auth/security.py`（344, 353 行）
- **修复**: 将 `import json` 提到模块顶层，删除函数内导入
- **价值**: 符合 PEP 8 导入规范，消除反模式

**P3-12: 日志器获取方式不统一（评估为合理设计）**
- **涉及文件**: 16 处非 `__name__` 命名
- **评估**: 均为合理设计（audit 模块统一日志聚合、CLI 入口、装饰器动态获取、插件动态 logger、类名 logger），跳过

**P3-13: auto-imports.d.ts @ts-nocheck（延后）**
- **原因**: IDE 自动生成文件，不应手工修改

**P3-14: 测试代码 : any（跳过）**
- **原因**: 影响有限，前端 19 处主要在 mock 构造中，与生产代码无关
