## 一、系统架构总览

### 1.1 架构模式

灵境制造采用**桌面应用 + Sidecar 微服务**架构（V2.0.0 收敛版）：

```
┌─────────────────────────────────────────────────┐
│                  Tauri 2 桌面应用 (V2.0.0)       │
│  ┌───────────────────────────────────────────┐  │
│  │  Vue 3 前端 (WebView2)                    │  │
│  │  ├── Three.js 3D 渲染                    │  │
│  │  ├── Element Plus UI                     │  │
│  │  ├── Pinia 状态管理 (12 个 Store 模块)     │  │
│  │  └── 11 个路由（含 404 兜底）              │  │
│  └───────────────────────────────────────────┘  │
│  ┌───────────────────────────────────────────┐  │
│  │  Rust 后端 (Tauri Core) - 扁平模块         │  │
│  │  ├── Sidecar 进程管理 (7 个 Tauri 命令)   │  │
│  │  │   ├── start_backend / stop_backend     │  │
│  │  │   ├── restart_backend / ping_backend   │  │
│  │  │   └── get_backend_state / get_app_version / get_backend_port│
│  │  └── 健康检查客户端 (reqwest, 仅 ping 用)  │  │
│  └───────────────────────────────────────────┘  │
├─────────────────────────────────────────────────┤
│                  Python Sidecar (FastAPI)       │
│  ┌───────────────────────────────────────────┐  │
│  │  FastAPI Web Server (27 个 include_router) │  │
│  │  ├── LNN 引擎 (CFC/LTC/Hybrid/Parameter)  │  │
│  │  ├── 模型注册系统 (LNNModelRegistry)       │  │
│  │  ├── LNN 训练器 (PyTorch + AMP + 量化)    │  │
│  │  ├── Uniwear 数据集处理                   │  │
│  │  ├── 工艺规划 / 加工仿真 / 规则引擎        │  │
│  │  ├── Agent / RAG / 模板 / 插件 / 治理     │  │
│  │  ├── Prometheus 指标 (MetricsMiddleware)  │  │
│  │  └── IdleAutoShutdown (1800s)            │  │
│  └───────────────────────────────────────────┘  │
├─────────────────────────────────────────────────┤
│                  Ollama (可选)                   │
│  ┌───────────────────────────────────────────┐  │
│  │  本地 LLM 推理服务 (ai/ollama_routes.py)   │  │
│  └───────────────────────────────────────────┘  │
└─────────────────────────────────────────────────┘
```

> **V2.0.0 关键收敛**：Rust 后端职责从"文件系统 + 进程管理 + 持久化 + HTTP 代理"四方职责，**收敛为"Sidecar 进程管控 + 应用信息查询"两点职责**（共 7 个 Tauri 命令）。文件操作、设置/项目管理、HTTP 代理已全部下沉至 Python FastAPI 端，前端通过 `http://127.0.0.1:8000/api/v1/*` 直接调用。Rust 仅保留 `reqwest` 用于 `ping_backend` 命令的存活探测。

## 三、Rust 后端架构

### 3.1 模块架构

```
src-tauri/src/
├── main.rs          # 应用入口、Tauri 配置、命令注册
├── lib.rs           # 库入口（lib crate）、共享状态与生命周期
├── commands.rs      # Tauri 命令注册中心（统一导出）
├── sidecar.rs       # Sidecar 进程管理
└── （不再使用 commands/ 子目录，已合并为扁平模块）
```

### 3.2 数据模型

**文件**: `src-tauri/src/commands.rs`

核心模型：
- `AppState` - 全局状态包装（V2.0.0 简化版，仅包含 sidecar 引用）
- `BackendState` - 后端进程状态（running、pid、port、started_at）
- `BackendStatus` - 后端状态枚举（Stopped/Starting/Running/Crashed）
- `SidecarManager` - Sidecar 进程管理器（封装启动/停止/重启/健康检查）
- `SidecarConfig` - Sidecar 配置（python_path、host、port、log_dir）

详细数据模型与业务命令请参见 [01-综合技术文档.md §6 Rust 后端模块设计](#)。

### 3.3 应用状态

**文件**: `src-tauri/src/commands.rs`

```rust
/// 全局状态包装（V2.0.0 简化版）
pub struct AppState {
    pub sidecar: Arc<SidecarManager>,
}
```

- `AppState` 是 V2.0.0 引入的轻量级状态包装，仅持有一个 `Arc<SidecarManager>` 引用
- 所有 Sidecar 状态（PID、端口、运行状态、重启计数等）下沉到 `SidecarManager` 内部，使用 `parking_lot::Mutex` 保护
- 通过 `tauri::Builder::manage(app_state)` 注册为全局状态，前端通过 `invoke()` 调用的命令可使用 `State<'_, AppState>` 获取

### 3.4 Tauri 命令

V2.0.0 起 Rust 后端采用**扁平化**架构，命令注册大幅精简。当前通过 `tauri::generate_handler!` 注册 **7 个命令**（全部位于 `src-tauri/src/commands.rs`），主要聚焦在 Sidecar 进程管理与基础应用信息查询：

| # | 命令 | 说明 | 签名 |
|---|------|------|------|
| 1 | `get_backend_state` | 查询后端进程状态（running、pid、port、status） | `fn(state) -> BackendState` |
| 2 | `start_backend` | 主动启动 Python Sidecar | `async fn(app, state) -> Result<BackendState, String>` |
| 3 | `stop_backend` | 主动停止 Python Sidecar（优雅终止） | `async fn(app, state) -> Result<BackendState, String>` |
| 4 | `restart_backend` | 重启 Sidecar（先 stop 再 start） | `async fn(app, state) -> Result<BackendState, String>` |
| 5 | `ping_backend` | 健康检查（HTTP `/api/health/ping`） | `async fn(state) -> Result<bool, String>` |
| 6 | `get_app_version` | 获取 Tauri 应用版本号 | `fn(app) -> String` |
| 7 | `get_backend_port` | 获取后端监听端口 | `fn(state) -> u16` |

> V2.0.0 重要变更：原 V1.x 的 30+ 命令（文件操作、HTTP 代理、健康检查诊断、项目管理、设置、日志导出等）已被移除。文件操作、设置管理、项目元数据等能力由 **Python FastAPI 后端**直接提供，Rust 层仅保留 Sidecar 进程管控与最小化的应用信息查询。

## 六、通信架构

### 6.1 通信链路

```
前端 (Vue) 
    │ ← Tauri invoke() / HTTP 请求
    ↓
Rust (Tauri Core)
    │ ← HTTP 代理
    ↓
Python (FastAPI)
    │ ← HTTP 请求
    ↓
LNN 引擎 / Ollama (LLM)
```

### 6.2 延迟分析

| 通信路径            | 延迟             | 说明             |
| --------------- | -------------- | -------------- |
| 前端 → Tauri      | ~1ms          | IPC 序列化开销      |
| Tauri → Python  | ~5-20ms       | HTTP 请求 + 反序列化 |
| Python → LNN   | ~1-50ms       | LNN 推理（视模型大小）  |
| **全链路**         | **~7-71ms** | 累积延迟           |

### 6.3 HTTP 代理

> V2.0.0 起 HTTP 代理能力已下沉到前端。前端 Vue 通过 `fetch`/`axios` 直接请求 Python FastAPI 的 8000 端口，不再经过 Rust 中转（`reqwest` 仍保留用于 `ping_backend` 健康检查的 HTTP 客户端）。

**直连链路**：
- 前端 → `http://127.0.0.1:8000/api/v1/...` → Python FastAPI 路由
- 前端 → `http://127.0.0.1:8000/api/health/ping` → 健康检查
- Rust 端 `reqwest` 仅在 `ping_backend` 命令中使用（探测后端存活）

该调整消除了 V1.x 时代 HTTP 代理带来的额外序列化与中转延迟（~5-20ms），并简化了 Rust 端的依赖与命令面。

### 8.2 数据流

#### LNN 推理流程

```
用户输入（切削参数/特征数据）
    │
    ├── 数据预处理（标准化、特征提取）
    │
    ├── 模型选择（CFC/LTC/HybridLNN）
    │   │
    │   ├── 从注册表获取模型
    │   ├── 加载模型权重
    │   └── 执行推理
    │
    ├── AMP 推理（如支持）
    │
    └── 后处理（置信度计算、结果格式化）
        │
        └── 返回预测结果
```

#### LNN 训练流程

```
准备数据集（CSV/HDF5）
    │
    ├── 数据加载和预处理
```
