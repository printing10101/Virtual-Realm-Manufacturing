## 三、性能瓶颈分析

### 3.1 通信链路瓶颈

#### 3.1.1 问题描述

用户操作需要经过四层传递：前端 → Tauri/Rust → Python/FastAPI → Ollama，每层都涉及数据序列化/反序列化。

#### 3.1.2 延迟分析

```
前端 → Tauri IPC:     ~1ms    (JSON 序列化/反序列化)
Tauri → Python HTTP:  ~5-20ms (HTTP 请求 + 网络栈 + 反序列化)
Python → Ollama HTTP: ~50-500ms (LLM 推理，视模型大小)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
全链路累计:            ~56-521ms
```

#### 3.1.3 根因分析

1. **序列化开销**: JSON 序列化/反序列化在各层重复执行
2. **HTTP 协议开销**: Tauri → Python 使用 HTTP 协议，存在 TCP 握手、请求头传输等开销
3. **同步等待**: 前端调用 Tauri 命令为同步等待模式，无法并行处理

#### 3.1.4 影响范围

- AI 对话操作：用户感知明显延迟
- 工艺规划工作流：六 Agent 顺序执行，总耗时可能达到 30-120 秒
- 文件操作：相对影响较小（~20ms）

### 3.2 Three.js 渲染瓶颈

#### 3.2.1 已优化项

| 优化项 | 状态 | 说明 |
|--------|------|------|
| 资源释放 | ✅ 已完成 | 组件卸载时释放 geometry/material/renderer |
| 像素比限制 | ✅ 已完成 | `Math.min(devicePixelRatio, 2)` |
| 材质升级 | ✅ 已完成 | `MeshStandardMaterial` 替代 `MeshPhongMaterial` |

#### 3.2.2 仍存瓶颈

| 问题 | 影响 | 严重程度 |
|------|------|---------|
| 无模型 LOD（细节层次） | 大模型渲染帧率下降 | 高 |
| 无模型压缩加载 | 加载时间较长 | 中 |
| 场景灯光未优化 | 多光源下渲染性能下降 | 低 |
| 无 WebGL 上下文管理 | 多实例时可能冲突 | 低 |

### 3.3 Python 后端瓶颈

#### 3.3.1 Agent 顺序执行

六 Agent 顺序执行，每个 Agent 都调用 LLM，总耗时为各 Agent 耗时之和：

```
UnderstandingAgent:  ~5-15 秒
PlanningAgent:       ~10-20 秒
ParameterAgent:      ~5-15 秒
NCAgent:             ~10-30 秒
VerificationAgent:   ~5-15 秒
RepairAgent:         ~5-10 秒
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
总计:                ~40-105 秒
```

#### 3.3.2 知识库检索开销

每次 Agent 执行前都从 ChromaDB 检索相关知识：

```python
# 每个 Agent 都会执行
knowledge_results = self.knowledge_base.query(
    query_text="...",
    n_results=5
)
```

- ChromaDB 向量检索耗时：~50-200ms
- 6 个 Agent × 200ms = ~1.2 秒额外开销

#### 3.3.3 异步实现不完整

FastAPI 虽为异步框架，但部分操作可能阻塞事件循环：

- ChromaDB 部分操作为同步调用
- 文件操作未使用 `aiofiles` 异步库

### 3.4 数据存储瓶颈

#### 3.4.1 SQLite 并发限制

```rust
pub struct Database {
    conn: Mutex<Connection>,  // 互斥锁导致串行化
}
```

- `Mutex<Connection>` 导致所有数据库操作串行执行
- 高并发场景下成为瓶颈（虽然当前场景并发不高）

#### 3.4.2 索引缺失

```sql
-- 当前仅主键索引
CREATE TABLE projects (
    id TEXT PRIMARY KEY,  -- 自动索引
    name TEXT NOT NULL,
    -- 其他字段无索引
);
```

- 按名称、状态、创建时间查询时无法利用索引
- 项目数量增长后查询性能下降

## 六、优化方案

### 6.1 通信链路优化

#### 方案 1：使用 Tauri Events 替代 HTTP（推荐）

**目标**: 减少 Tauri → Python 的 HTTP 开销

```rust
// 前端通过 Tauri Events 订阅 Python 响应
listen('python-response', (event) => {
  // 直接接收数据，无 HTTP 开销
})

// Python 通过 Tauri emit 发送事件
app.emit_all("python-response", data)?;
```

**预期效果**: 延迟降低 ~5-10ms

#### 方案 2：批处理请求

**目标**: 减少多次小请求的累积开销

```typescript
// 将多个设置项合并为一次请求
await saveSettingsBatch({
  theme: 'dark',
  language: 'zh-CN',
  model: 'qwen2.5:7b'
})
```

**预期效果**: 减少 30-50% 的请求次数

#### 方案 3：gRPC 替代 HTTP（长期）

**目标**: 使用 Protocol Buffers 替代 JSON，减少序列化开销

| 对比项 | HTTP+JSON | gRPC+Protobuf |
|--------|-----------|---------------|
| 序列化大小 | 100% | ~30-50% |
| 延迟 | 基准 | -20-30% |
| 实现复杂度 | 低 | 高 |

**预期效果**: 延迟降低 ~20-30%，包体积减少 50-70%

### 6.2 工作流并行优化

#### 方案 1：ParameterAgent 与 NCAgent 并行

当前 `ParameterAgent` 和 `NCAgent` 可部分并行：

```python
async def execute_workflow_parallel(self, user_input: str):
    # 1-3: 顺序执行
    context = await self.understanding(context)
    context = await self.planning(context)
    context = await self.parameter(context)
    
    # 4-5: 可并行（NC 生成和验证可同时进行）
    nc_task = asyncio.create_task(self.nc_generation(context))
    verify_task = asyncio.create_task(self.verification(context))
    
    nc_result, verify_result = await asyncio.gather(nc_task, verify_task)
```

**预期效果**: 工作流总耗时减少 15-25%

#### 方案 2：知识库预加载与缓存

```python
class KnowledgeCache:
    def __init__(self):
        self.cache = {}  # query_hash -> results
    
    def get(self, query_text: str):
        cache_key = hashlib.md5(query_text.encode()).hexdigest()
        if cache_key in self.cache:
            return self.cache[cache_key]
        # 否则从 ChromaDB 检索
```

**预期效果**: 减少知识库检索开销 ~80%

### 6.4 Python 后端优化

#### 方案 1：异步 ChromaDB 操作

```python
import asyncio
from concurrent.futures import ThreadPoolExecutor

class AsyncKnowledgeBase:
    def __init__(self):
        self.executor = ThreadPoolExecutor(max_workers=2)
    
    async def query_async(self, query_text: str, n_results: int = 5):
        loop = asyncio.get_event_loop()
        return await loop.run_in_executor(
            self.executor,
            lambda: self.kb.query(query_text, n_results)
        )
```

**预期效果**: 避免阻塞事件循环，提升并发处理能力

#### 方案 2：Agent 代码复用

```python
class BaseAgent(ABC):
    async def _call_llm(self, system_prompt: str, user_content: str) -> dict:
        """统一的 LLM 调用和 JSON 解析逻辑"""
        messages = [
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": user_content}
        ]
        response = await self.llm_client.chat_completion(
            messages=messages, max_tokens=2048, temperature=0.3
        )
        return self._parse_json_response(response["content"])
    
    def _parse_json_response(self, content: str) -> dict:
        """统一的 JSON 解析和降级逻辑"""
        try:
            if "```json" in content:
                content = content.split("```json")[1].split("```")[0].strip()
            elif "```" in content:
                content = content.split("```")[1].split("```")[0].strip()
            return json.loads(content)
        except Exception:
            return {}
```

**预期效果**: 代码量减少 ~30%，维护成本降低
