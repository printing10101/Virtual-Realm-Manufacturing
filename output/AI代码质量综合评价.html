三、初评发现的 AI 编程常见缺点（2026-08-02 记录，多数已修复）

以下为初评（52/C）时发现的核心缺陷记录。截至复评（66/B-），①⑧已全部修复、②④⑤⑦已大幅缓解（见第五节状态表）。保留此节作为历史基线。

① 静默吞异常 —— 最严重且最典型的 AI 缺陷 P0/P1

AI 在"不确定如何处理错误"时，倾向于写 except Exception: pass 或仅 logger.warning(e) 然后继续。本项目 1,391 个 except 中约 824 个（59%）的 catch 体无任何恢复逻辑。后果：运行时故障被掩盖，排障靠"猜"，且多数集中在核心路径（DNC/OPC UA 客户端、仿真、LNN 训练执行器）。

② 错误抑制而非修复 —— type:ignore / noqa P2

372 处类型/lint 抑制注释，数量不小。部分确属已知误报，但相当比例是 AI "用注释让红色波浪线消失"而非真正解决类型错误。这类抑制会随重构悄悄失效，且使静态检查失真。

③ 分层退化 —— 架构契约被"能跑就行"绕过 P1

AI 逐文件生成时不会维护全局分层。结果是：11+ 个非 API 包自行定义 APIRouter（simulation/api.py、rag/routes.py、dxf/api.py、projects/project_api.py…），由 API 层直接 re-export；9 个 API 文件直连 DB/ORM 绕过服务层；前端 19 个视图直接 import http，而精心设计的 features/ 抽象层 0 个视图使用。main.py 还用 @app.get 直接注册 6 条路由绕过 api/v1 结构。

④ 全局单例泛滥 —— 依赖未注入 P1

214 个 get_*() 工厂作为模块级单例。AI 偏好"一处定义、全局 import"，导致隐式耦合、测试需大量 mock、并发初始化竞态（此前 init_db 自旋死锁即源于此）。应改用 FastAPI Depends 注入。

⑤ 僵尸契约层 + 重复目录 —— 建了却没接 P2
